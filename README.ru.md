# Hisense VIDAA (MT9603) — заметки по реверсу

Это записки о том, как устроен телевизор Hisense на платформе VIDAA с чипом
Mediatek MT9603, если смотреть на него не через меню, а через его же файлы,
службы и протоколы. Всё собрано на своём телевизоре, без перепрошивки и без
изменения его состояния: задача была понять, что внутри и как оно
разговаривает, а не сломать защиту любой ценой.

Английская версия: [`README.md`](README.md).

## С чего всё началось

Прямых файлов прошивки под конкретную модель в открытом доступе нет. На сайтах
Hisense — только форма запроса в сервис, сторонние архивы вроде FileWale и
HalabTech просят денег и аккаунта, а публичные зеркала содержат другие
линейки. Рабочий путь оказался скучным: письмо в поддержку Hisense по
серийному номеру, и через несколько дней — ссылка на скачивание файла
`MstarUpgrade.bin` размером почти гигабайт.

Первое, что дал этот файл, — не содержимое, а ясность: образ подписан и
зашифрован, ключа внутри нет, и всё, что можно узнать о файловой системе,
придётся добывать с самого телевизора. Второе — страховка: если эксперименты
с устройством закончатся плохо, есть чем восстановить ровно ту версию,
которая на нём стояла.

## Что за телевизор

| | |
|---|---|
| Строка модели | `65Q60SEVS_01` |
| SoC | `MTK9603` (Mediatek, ARMv7) |
| Версия ПО | `V0000.09.60V.Q0612` |
| Сборка | `a20260727` |
| Регион | `EU_A` |
| VIDAA SDK | `1.5.0` |
| Браузер | Chromium 111, токены UA `SurfMaster`, `PageReader`, `ViewPort` |

Серийный номер, device ID, capability- и feature-коды, MAC-адреса и адреса
локальной сети из репозитория убраны: к устройству платформы они отношения не
имеют, зато однозначно указывают на конкретный экземпляр.

## Что удалось выяснить

Прошивка устроена как подписанный контейнер. Первые 256 байт — блок подписи
RSA, дальше версия упаковщика и две директивы открытым текстом: где начинается
полезная нагрузка и какой она длины. Сама нагрузка — шифротекст с энтропией
почти восемь бит на байт, без единой сигнатуры архива или файловой системы. В
хвосте файла открытым текстом лежит манифест: платформа, версия, чип,
производитель. То есть формат читается, а содержимое — нет.

Популярные инструменты для MTK-пакетов здесь не работают. `epk2extract` ищет
магик `hise` в нулевом байте, а там подпись; его встроенные «generic»-ключи
дают мусор во всех режимах. REA для работы с прошивками требует binwalk и всё
равно режет по сигнатурам, которых нет. Подробный разбор с цифрами — в
[первом документе](docs/ru/01-firmware-container.md).

Второй слой, и самый интересный, — веб-часть. Любая страница, открытая в
браузере телевизора, живёт в окружении, куда производитель выставил мост из
96 функций: версия прошивки, модель, панель, регион, TTS, субтитры, громкость,
наблюдатели за изменением свойств. Всё это — геттеры поверх одного нативного
`TvInfo_getParam`. Знаменитых `Hisense_FileRead`, `File` и
`Hisense_installApp`, на которых держались публикации 2017 года, в этой
прошивке просто нет, и это сразу закрывает старые рецепты.

Зато есть то, чего в старых разборах не было. На телевизоре работает локальный
HTTP-API `https://localhost:9888/service/<имя>`, и он отвечает странице с
чужого origin. Служб ровно три: `pkgmgr`, `hiutils`, `tvinfo`. Через `tvinfo`
читается состояние телевизора, через `pkgmgr` — список установленных пакетов с
путями вида `APPS:pkgs/…`, а через `hiutils` — то, ради чего всё затевалось:
`fileRead` и `fileWrite`.

И вот здесь исследование упирается. `fileRead` разрешён и честно лезет в
файловую систему, но собирает путь от корня приложения, а для страницы, которая
не является установленным приложением, этот корень равен `undefined`.
`fileWrite`, `deviceCode` и `uninstallApp` отбиваются проверкой
`client request permission check error, please check appconfig`. Подменить
идентичность из JavaScript не удаётся: служба берёт её из нативного
`vowOSContext`, а нативный `init()` для обычной страницы возвращает `-1`.
Подробности и таблица попыток — в [четвёртом документе](docs/ru/04-identity-gate.md),
чтобы не проходить этот путь заново.

## Чем всё закончилось

Веб-слой отдал всё, что мог: карту моста, три службы, их белый список api,
формат сообщений протокола `phoenix://` и точное место, где стоит проверка
прав. Не отдал главного — доступа к файлам и пути на запись.

Дальше начинается территория, где нужна отвёртка: UART, шелл загрузчика, дамп
раздела с ключом. Пока этих данных нет, и раздел про UART здесь не заведён —
пустых обещаний в репозитории не держим. Если дело дойдёт, документ появится
вместе с результатами.

## Что лежит в репозитории

```
docs/      разбор по темам, один файл на тему; docs/ru — то же по-русски
samples/   очищенные выводы проб с устройства, JSON
tools/     HTML-страницы проб, которыми это собрано
```

Страницы из `tools/` обращаются только к тому серверу, который их отдал, и
вызывают только чтение: `fileRead`, `getOSVersion`, `getVersionStatus`,
`deviceCode`, `getInstalledPkgs`, `tvinfo.initialData`. Ни записи, ни
установки, ни удаления в них нет — это видно по исходникам.

Образ прошивки в репозиторий не положен: он гигабайтный, GitHub такие файлы не
принимает, и это чужой бинарник. Вместо него — размер, SHA-256 и раскладка
заголовка: свою копию, полученную у поддержки производителя, любой может
сверить с этими числами.
