# 1. Контейнер прошивки (`usb_*.bin` / `MstarUpgrade.bin`)

**English version: [docs/01-firmware-container.md](../01-firmware-container.md)**

Образ получен у поддержки Hisense по запросу, доставлен немецким дистрибьютором
ссылкой на подписанное скачивание Salesforce. Ничего из описанного не требует
именно этого файла: свою копию можно проверить по хешу ниже.

| | |
|---|---|
| Имя файла | `MstarUpgrade.bin` (он же распространяется как `usb_MTK_9603_EU_4K_2G_3_YT25.bin`) |
| Размер | 1 005 336 192 байт (`0x3bec3680`) |
| SHA-256 | `f366894eadf26f79fc85d0bb06cd2c35bc171a539ebdd3f440f0ef2ec452c5ac` |

## Раскладка

```
0x000000  256 байт       блок подписи RSA-2048 (непрозрачный)
0x000100  "V_0.0.0"      версия упаковщика, добита нулями до 0x300
0x000302  открытым текстом  "# REE_OFFSET_START = 0x1000 #\n# REE_OFFSET_LEN = 0x3bec0000 #\n"
0x001000  нагрузка       AES-тело, 0x3bec0000 байт
0x3bec1000 хвост         подпись и манифест, 9856 байт
```

Манифест, печатные строки в хвосте:

```
0x3bec3400  MTK_9603_EU_4K_2G_3_YT25
0x3bec3420  V0000.09.60V.Q0612
0x3bec3480  MT9603DB
0x3bec34a0  Hisense
```

В хвосте также 492 байта `0xFF`, 166 нулевых байт и 46 коротких случайных
печатных последовательностей — это согласуется с подписью плюс манифестом с
фиксированными полями, но не со сжатыми данными.

## Анализ нагрузки

| Проверка | Результат |
|---|---|
| Энтропия Шеннона, окна по 4 МиБ на 0x1000 / 0x100000 / середине / конце | 7,9999 – 8,0000 |
| Повторы 16-байтных блоков на выборке 64 МиБ | 0 (4 194 303 уникальных) |
| Повторы 512-байтных блоков, 64 МиБ | 0 |
| Нулевые байты в нагрузке | 0,4 % |
| Сигнатуры gzip / bzip2 / xz / zip / tar / squashfs / UBIFS / ELF / `ANDROID!` / `CrAU` | ничего осмысленного |
| `binwalk` 2.4.3 (первые 128 МиБ) | только ложные попадания «JBOOT STAG» |

Нагрузка с полной энтропией и **без повторов блоков** означает CBC/CTR/XTS, а не
ECB — значит атака по словарю повторяющихся блоков открытого текста невозможна.

## Почему обычные инструменты для Hisense/MTK не подходят

**`epk2extract`** (`openlgtv/epk2extract`) определяет MTK-пакеты по магику
вендора в **нулевом байте**:

```c
#define HISENSE_PKG_MAGIC "hise"
#define MTK_FIRMWARE_MAGIC "#DH@FiRm"
#define MTK_PAK_MAGIC      "iMtK8"
```

Скан всех 1 005 336 192 байт: `hise` — 0 попаданий, `#DH@FiRm` — 0, `iMtK8` — 0;
ветка `is_firm_image()` ждёт заголовок LZHS после заголовков прошивки. Этот
контейнер — не тот формат. Его встроенные ключи (`keys/MTK.key`) — публичные
«Mediatek generic»-ключи AES-128: `09291094…`, `53686172…` (Sharp),
`5450565F…` (TPV). Применённые к нагрузке в ECB, CBC и CTR они дают печатный
мусор без узнаваемых магиков. README проекта говорит прямо: для зашифрованных
версий ключи надо *«dump them from a running TV»*.

**REA** (`morlua/rea` / `rea-agents` 6.4.0) имеет `inspect-firmware-regions` и
`extract-firmware`, но обе команды вызывают binwalk и отказываются работать без
абсолютного пути в `REA_BINWALK_COMMAND`. Даже с подключённым binwalk извлечение
идёт по сигнатурам, а сигнатур, по которым можно резать, здесь нет.

**Перебор фиксированных ключей** (DES-ECB обоими ключами, AES-128-ECB с
`0123456789ABCDEF` и нулями, AES-256-ECB) тоже не даёт результата.

## Вывод

Тело офлайн не расшифровать. Ключ живёт на устройстве — в boot-разделе или в
eFuse, — поэтому любая дальнейшая работа требует доступа со стороны устройства
(UART, шелл загрузчика или дамп ключа с работающей системы). Сам файл остаётся
полезен как образ восстановления для точной модели и версии и как эталон для
сравнения, когда ключ появится.
