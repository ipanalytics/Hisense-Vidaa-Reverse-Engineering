# 4. Гейт идентичности и appconfig

**English version: [docs/04-identity-gate.md](../04-identity-gate.md)**

Всё привилегированное на этой прошивке отказывает одной и той же фразой:

```json
{"ret":false,"msg":"client request permission check error, please check appconfig","code":503}
```

Формулировка «please check appconfig» и есть подсказка: служба проверяет не
то, что вызывают, а то, кто вызывает. Конфигурация приложения — `appconfig` —
ставится вместе с самим приложением и содержит его права. У страницы,
открытой в браузере, такой конфигурации нет, поэтому отказ.

## Откуда берётся идентичность

Вот функция из SDK целиком:

```js
function() {
    if(window.navigator.appIdentifier !== 'undefined' &&
       window.vowOSContext &&
       typeof(window.vowOSContext?.getAppIdentifier) === 'function') {
        return window.vowOSContext.getAppIdentifier()
    }
    return ''
}
```

На обычной странице нативный контекст существует, но пуст:

```
vowOSContext = { init, getAppIdentifier, getAppId }   — все [native code]
getAppIdentifier() -> ""
getAppId()         -> ""
init()             -> "-1"
navigator.appIdentifier — геттер на прототипе Navigator, отдаёт undefined
```

Значение `-1` из `init()` объясняет всё остальное. Инициализация нативного
контекста не прошла, потому что документ не создан как установленное
приложение. Привязки идентичности не случилось, и всем последующим проверкам
не с чем сверяться.

## Что можно подделать и что из этого выходит

Сначала оказалось, что подмена возможна на уровне JavaScript. Свой
`vowOSContext` с функцией `getAppIdentifier` действительно меняет то, что
отдаёт `getIdentifier()` — проверено, возвращалось подставленное значение.
Правда, одной этой подмены мало: в условии выше стоит ещё проверка
`window.navigator.appIdentifier !== 'undefined'`, а на телевизоре там лежит
именно **строка** `"undefined"`, и сравнение с ней даёт ложь. Пришлось
переопределять и геттер на прототипе `Navigator` — собственное свойство на
объекте `navigator` перекрывает прототип, и это работает.

Результат одинаковый для всех вариантов:

| Подставленная идентичность | `deviceCode` по HTTP | `deviceCode` по WebSocket | корень в `fileRead` |
|---|---|---|---|
| `tv.vidaa.app.browser` | 503 | 503 | `undefined` |
| `tv.vidaa.res.iot` | 503 | 503 | `undefined` |
| `system`, `root`, `vidaa`, `hisense` | 503 | 503 | `undefined` |
| пустая строка | 503 | 503 | `undefined` |

Вывод: строку `identifier` в теле сообщения и в заголовке служба сама по себе
не доверяет. Либо она сверяет её с регистрацией, которую провела раньше на
нативном уровне, либо просто не смотрит на неё, а опирается на контекст
процесса, недоступный из JavaScript.

Ещё две попытки, обе мимо:

- `execute('phoenix://service/hiutils', {method:'register', …})` через SDK
  невозможен: `execute()` требует `parameters.api` и возвращает `false` до
  отправки. Но если открыть **свой** `wss://localhost:9888` и послать то же
  тело руками, служба отвечает, и `register` принимается:

  ```
  сессия 9002  register + api=getOSVersion  -> {"msg":"registered","code":0}
  сессия 9004  register + api=initialData   -> {"msg":"registered","code":0}
  сессия 9003  register + api=deviceCode    -> 503 appconfig
  сессия 9001  callAPI  + api=deviceCode    -> 503 appconfig
  ```

  То есть регистрация существует и закрепляется (SDK такие сессии не удаляет),
  но прав не даёт: регистрация привилегированного api возвращает тот же 503,
  что и обычный вызов. Гейт идентичности состоянием протокола не обходится.
- `GET https://localhost:9888/` отвечает `service register failed`. Точка
  регистрации есть, но неаутентифицированный вызов она отвергает.

## Почему это конец веб-пути

Дело не в баге, который можно обойти аккуратной строкой. Идентичность
приложения устанавливается нативно в момент создания документа, до того как
исполнится первый байт JavaScript. Страница не может повысить себя до
приложения, и никакого видимого из JS способа выдать себе права нет.

Остаются два пути, и оба вне браузера. Либо получить документ, отрисованный
как установленное приложение — на старых прошивках это делал отладочный
обработчик, но здесь сами установочные вызовы отвечают 503, так что дверь
заперта изнутри. Либо исполнять код на уровне ниже браузера, что выходит за
рамки этого документа. И то и другое — работа с устройством, а не трюк в
протоколе.
