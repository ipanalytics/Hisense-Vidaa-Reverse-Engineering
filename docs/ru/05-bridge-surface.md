# 5. Поверхность моста: 96 функций

**English version: [docs/05-bridge-surface.md](../05-bridge-surface.md)**

Любая страница, отрисованная браузером телевизора, получает в `window` набор
функций производителя. Инвентарь собирается обходом `window` по шаблонам имён
(`Hisense_*`, `HiUtils*`, `Hi[A-Z]*`, `File`, `Vidaa*`, `WebAp*`) и печатью
`Function.prototype.toString()` для каждой. Они написаны на обычном
JavaScript, поэтому исходники видны целиком — декомпилировать нечего.

Всего нашлось 96 функций.

## Что есть

**Геттеры `Hisense_Get*` — их около восьмидесяти.** Каждый представляет собой
одну строку поверх нативного `TvInfo_getParam('<ключ>')`: имя модели, бренд,
регион, страна, разрешение панели, версия прошивки, чип, тип серийного
номера, device ID, feature- и capability-коды, состояние сети, IP-адрес,
громкость и mute, параметры TTS, состояние субтитров и закрытых титров, флаг
hotel-режима. Никакой логики, кроме чтения свойства, в них нет.

**Сеттеры `Hisense_Set*`** — громкость, удалённая клавиатура, стартовая
полоса пропускания, включение и выключение экранной клавиатуры.

**Наблюдатели** — `Hisense_RegisterObserver` и `UnregisterObserver`, пары
ключ-колбэк на изменение свойства. `Hisense_RegisterVolumeObserver` —
обёртка над тем же для `soundVolume`.

**`Hisense_LoginWithVIDAA(apptype, cb)`** — отправляет через платформенный
канал сообщение
`{"type":"APPMessage","MsgType":"account","action":"loginWithVidaa",…}`.

**`HiUtils_createRequest(type, msg)`** — та самая лазейка в нативную службу,
через которую работает всё остальное.

## Чего нет

По сравнению с файловой системой VIDAA 2017 года, которая ходит по рукам
публично, три точки входа исчезли:

```
typeof Hisense_FileRead    → undefined
typeof File                → function   (это DOM-конструктор File, не объект моста)
typeof Hisense_installApp  → undefined
```

Именно из-за этого старый опубликованный приём — поставить HTML5-приложение
через `hisense://debug` и читать файлы через мост — на этой ревизии не
работает.

С `File` есть ловушка, на которую легко попасться. `typeof File === 'function'`
выполняется, и из этого хочется сделать вывод «файловый API есть». Но это
DOM-конструктор, у которого нет и никогда не было метода `read`. Правильная
проверка — `typeof File.read === 'function'`, и она даёт `undefined`.

## Платформенные объекты

`omi_platform` выставляет ровно два метода: `addPlatformEventListener` и
`sendPlatformMessage`. Через второе уходят сообщения вида `restartWebsocket`
и `APPMessage`.

`vowOS` состоит из трёх частей:

```
vowOS.service   — мост phoenix (см. 03-phoenix-protocol.md)
vowOS.tvinfo    — геттеры и сеттеры поверх TvInfo_getParam/SetParam
vowOS.store     — getInstalledPkgs, installApp, sendPkgmgrRequest
```

У `vowOS.tvinfo` есть и запись: `setKidsMode`, `setArtMode`, `setBrightness`,
`setContrast`, `setDabTools`. Ни одна из них в этом исследовании не
вызывалась — работа велась только на чтение. `vowOS.store.installApp` на этой
ревизии мёртв: внутри он обращается к `Hisense_installApp`, которого нет.

## Что это даёт на практике

Сами по себе 96 функций — это не доступ, а карта. Из них видно, какие
свойства платформа считает достаточно безопасными, чтобы отдавать их любому
документу: версии, модель, регион, состояние экрана и звука. Всё, что касается
файлов, кодов устройства и установки приложений, вынесено за пределы моста — в
службу `hiutils`, где стоит проверка прав.
